# 规范 Spec · 微信群 AI Agent（第一阶段：按需查询与总结）

> spec 模式产出。记决策与可验收行为，不写文件路径、不贴代码（易过时）。
> 日期：2026-09-10 ｜ 上游共识：clarify 共识小结（2026-09-10） ｜ 状态：已定稿

## 1. 问题是什么

微信群消息分散、数量大，手动翻群找信息耗时（典型场景：翻一个群的近期消息需要 40 分钟）。用户需要一种自然语言方式，快速查询指定群的历史消息、搜索关键词、获取 AI 总结，且全程不触发微信风控。

现状：微信小号已登录（4.1.8 版本），wx-cli 已安装并成功提取 16/18 个数据库密钥，但数据读取能力尚未验证，AI 总结工作流尚未配置。

## 2. 方案是什么

用 **wx-cli**（jackwener/wx-cli）读取微信小号的本地加密数据库（SQLite + SQLCipher），豆包理解用户自然语言意图后调用对应 wx-cli 命令，对返回数据做 AI 总结，在豆包对话中直接回答。全程只读本地文件，不碰微信进程、不联网、不操作微信界面，零风控风险。

整体链路：用户自然语言提问 → 豆包解析意图 → 调用 wx-cli（sessions/history/search/contacts/members/stats/attachments 等）→ 解析 JSON/YAML 输出 → AI 总结（默认简短要点 + 重要消息标注）→ 豆包对话回答。

## 3. 接缝 seam（在哪测）

- **选定的可独立测试接缝：wx-cli 命令行接口**
- 为什么是它：
  1. wx-cli 是唯一的数据入口，所有查询都通过它的命令完成，接口稳定（命令名和输出格式由 wx-cli 项目定义）
  2. 豆包侧的意图解析和 AI 总结逻辑可以被反复改写，但只要 wx-cli 命令调用正确、输出解析正确，整条链路就不会坏
  3. 测试只需验证：给定用户查询 → 是否调用了正确的 wx-cli 命令 → 输出是否被正确解析 → 总结是否覆盖核心信息
  4. 底层 wx-cli 版本升级或密钥重新提取，不影响上层测试用例

## 4. User Stories（每条都要能验收）

### 4.1 查询群历史消息并总结
- 作为用户，在想了解某个群最近讨论了什么时，系统应根据自然语言查询（如"XX群最近3天聊了什么"）调用 wx-cli history 获取该群指定时间范围的消息，AI 总结后在对话中回答，以便快速掌握群聊动态。
  - 验收：给定查询"产品群最近7天聊了什么"，系统应返回该群近7天消息的 AI 总结，包含核心话题（3-5条）和重要消息标注（@我/决策/紧急），且不遗漏关键讨论。

### 4.2 搜索消息关键词
- 作为用户，在想找某个话题在哪些群讨论过时，系统应根据自然语言查询（如"搜一下所有群里关于预算的消息"）调用 wx-cli search 搜索关键词，返回匹配的消息列表和所在群，以便快速定位信息。
  - 验收：给定查询"搜一下关于'季度总结'的消息"，系统应返回所有包含该关键词的消息，标注每条消息的群名、发送人、时间，并可按群或时间排序。

### 4.3 查看未读消息
- 作为用户，在想知道哪些群有未读消息时，系统应调用 wx-cli unread 返回有未读消息的会话列表，以便快速处理未读。
  - 验收：给定查询"有哪些未读消息"，系统应返回所有有未读消息的群/联系人列表，标注未读数量，可按未读数排序。

### 4.4 查看群成员
- 作为用户，在想知道某个群有哪些人时，系统应调用 wx-cli members 返回该群成员列表，以便了解群构成。
  - 验收：给定查询"产品群有哪些人"，系统应返回该群所有成员的昵称/备注列表，标注群管理员。

### 4.5 查看群统计
- 作为用户，在想了解某个群的活跃度时，系统应调用 wx-cli stats 返回该群的统计数据（消息数、活跃人数、活跃时段等），以便评估群价值。
  - 验收：给定查询"产品群最近一个月的活跃度怎么样"，系统应返回该群指定时间范围的统计数据，包括消息总数、参与人数、最活跃的人、消息类型分布。

### 4.6 查看图片/附件
- 作为用户，在想找某个群里发过的图片或文件时，系统应调用 wx-cli attachments + extract 列出并解密附件，以便找回资源。
  - 验收：给定查询"产品群最近发了哪些图片"，系统应返回该群指定时间范围内的图片附件列表，可按需解密导出到本地。

### 4.7 重要消息自动标注
- 作为用户，在阅读 AI 总结时，系统应自动标注重要消息（@我的消息、包含关键决策的消息、紧急事项），以便不遗漏重要信息。
  - 验收：任何群消息总结中，@用户的消息必须被标注；包含"决定/通过/截止/紧急"等关键词的消息应被标注为决策或紧急。

### 4.8 歧义确认
- 作为用户，在查询中群名有歧义时（如多个群包含"产品"二字），系统应反问确认具体指哪个群，而不是猜测。
  - 验收：给定查询"产品群聊了什么"且存在多个含"产品"的群时，系统应列出候选群让用户选择，不直接查询。

## 5. 实现决策（已定，含取舍）

- **只读不写**：第一阶段只做数据读取和 AI 总结，不做发消息、自动回复、加好友等写操作。放弃 UI 自动化发消息方案，因为操作微信界面有风控风险。
- **先按需查询，再主动监控**：第一优先级是用户主动提问触发查询；定时自动监控推送作为第二阶段。放弃一开始就做定时任务，因为先验证基础链路稳定性更重要。
- **第一阶段只在豆包对话回答**：不同步飞书文档/知识库。放弃一开始就做飞书同步，因为先验证核心价值，输出通道是次要的（飞书连接器已绑定成功，第二阶段可加）。
- **自然语言交互**：用户用自然语言提问，豆包解析意图后调用 wx-cli。放弃固定命令模板，因为自然语言在豆包对话中最自然，用户不需要记命令。
- **默认简短要点 + 重要消息标注**：总结默认 3-5 条核心结论，重要消息自动加粗标注；用户说"详细点"时切换到详细分类。放弃默认详细输出，因为大多数时候快速了解即可。
- **密钥提取方式：关 SIP + sudo + 不重签微信**：已验证成功（16/18 个密钥）。放弃 ad-hoc 重签微信方案，因为重签会改变 code identity，可能触发微信风控（之前重签后被强制下线+违规提示）。
- **微信版本锁定 4.1.8**：wx-cli 当前只支持 ~4.1.8，微信 4.1.10+ 改变了密钥存储格式导致提取失败。这是 wx-cli 的硬性限制，非主动选择不升级。
- **密钥长期有效**：同账号、同版本、不重装的情况下，密钥提取一次后永久有效，不需要重复扫描微信内存。仅在微信升级、切换账号、重装时重新提取。
- **用微信小号不用主号**：所有操作针对小号数据目录，不碰主号数据。

## 6. 测试决策

### 6.1 测试接缝
- **wx-cli 命令输出验证**：逐个验证 wx sessions / wx history / wx search / wx contacts / wx members / wx unread / wx stats / wx attachments 命令是否能正常输出数据，输出格式是否正确。
- **自然语言到命令的映射验证**：给定典型用户查询，验证是否调用了正确的 wx-cli 命令和参数。
- **总结质量验证**：给定已知内容的群消息，验证 AI 总结是否覆盖核心话题、是否正确标注重要消息、是否有遗漏。

### 6.2 覆盖边界
- **正常场景**：指定群名明确、时间范围明确、关键词明确的查询。
- **边界场景**：群名有歧义（多个群匹配）、时间范围超长（如一年）、关键词无匹配、群无消息。
- **异常场景**：wx-cli 命令失败（密钥失效/数据库损坏）、微信未运行、数据目录不存在。
- **风控验证**：读取操作过程中微信不弹警告、不被强制下线、读取后微信正常使用。

### 6.3 测试顺序
1. 先验证 wx-cli 基础命令（sessions → history → search → 其他）
2. 再验证自然语言意图解析
3. 最后验证 AI 总结质量
4. 全程监控微信状态，确保无风控异常

## 7. 不做什么（Out of scope）

- ❌ 不做发消息、自动回复、加好友、删好友等写操作（第一阶段）
- ❌ 不做定时自动监控推送（第二阶段再做）
- ❌ 不同步飞书文档/知识库（第二阶段再做）
- ❌ 不操作微信主号，只用小号
- ❌ 不重签微信、不持续注入进程、不高频扫描微信内存
- ❌ 不升级微信（锁定 4.1.8，wx-cli 硬性限制）
- ❌ 不做朋友圈发布、公众号发布等写操作
- ❌ 不做语音/视频消息的内容解析（只做文字和附件元数据）

## 9. 第二阶段计划（待规划，2026-09-10 纳入）

> 用户明确：主动监控推送先纳入计划，到时候讨论整体计划时一并考虑。以下为初步设想，**具体细节待第二阶段启动时再走 clarify 细化，当前不实现**。

### 9.1 主动监控推送（已纳入计划）
- **目标**：不用手动问，系统定时/准实时自动拉取指定群新消息，AI 总结后主动推送给用户。
- **技术基础**：`wx new-messages`（增量拉取自上次检查以来的新消息）+ 定时任务（doubao-cron-scheduler）+ 推送通道。
- **待第二阶段澄清的决策点**：
  - 监控哪些群（固定清单 vs 动态配置）
  - 触发频率（实时监听 / 定时如每小时 / 每天早晚汇总）
  - 推送通道（豆包消息 / Mac 通知 / 飞书消息）
  - 重要消息是否即时提醒（如@我立即推送，普通消息攒批汇总）
  - 与第一阶段按需查询能力如何复用同一套意图映射和总结模板
- **风控注意**：仍为只读，`wx new-messages` 读本地数据库，定时频率不宜过高。

### 9.2 飞书同步（已纳入计划）
- **目标**：把 AI 总结结果持久化到飞书知识库/文档（AI 分类）。
- **前置**：飞书连接器已绑定成功。
- **待澄清**：目标知识库位置、文档组织方式（按群/按日期/按话题）、更新策略（追加 vs 覆盖）。

### 9.3 第二阶段候选（视第一阶段使用情况决定）
- 写操作（发消息/自动回复）：需叠加 mac-system-toolkit 的界面自动化能力，有风控风险，用户谨慎，默认不做
- 附件/图片解密导出的更多场景
- 朋友圈、公众号的深度查询

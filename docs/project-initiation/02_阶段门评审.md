## G2 · 验证门：最小验证是否证明假设成立？

wechat-control 是工具/产品混合型，按"每阶段一个最小验证"评估。

### 阶段一 · 只读查询

**最小验证标准**：干净环境下 `wx sessions / history / search / unread / contacts` 五类只读命令能返回结构化结果，且不 crash、不写库。

| 领域 | 标准 | 是否通过 |
|---|---|---|
| 战略对齐 | 只读查询是否覆盖了"AI 接管微信信息面"的主需求？ | ✅ |
| 进度绩效 | 十类只读查询命令是否已全部实现并在用？ | ✅ |
| 风险状态 | 只读路径是否做到不碰进程、不联网、不写库？ | ✅ |
| 交付物合规 | `scripts/message-collector.py` 是否能解析 33 种消息类型？ | ✅ |

**决策**：**Go**（阶段一验证成立）

### 阶段二 · 主动监控与每日总结

**最小验证标准**：daemon 能持续监听新消息、每日产出一份摘要、重要性判定不误报炸群。

| 领域 | 标准 | 是否通过 |
|---|---|---|
| 战略对齐 | 每日总结是否减少了手动翻微信的时间？ | ✅（在用） |
| 进度绩效 | `realtime-monitor.py` + `wx-monitor.py` 是否上线并跑过完整周期？ | ✅ |
| 风险状态 | 监控是否纯读库、不发消息、不触发对方任何感知？ | ✅ |
| 交付物合规 | 推送渠道（控制台/日志/飞书）是否有失败重试？ | 🟡 部分（飞书 webhook 已通，Webhook 通用化规划中） |

**决策**：**Conditional Go**

| 条件 | 可测量标准 | owner | 截止日 |
|---|---|---|---|
| daemon 自愈与内存泄漏 | 连续运行 72 小时不僵死、RSS 增长 < 50MB | 本人 | 2026-10-01 |
| 重要性判定误报率 | 高优先级消息中"不重要"占比 < 10% | 本人 | 2026-10-15 |

### 阶段三 · 受控写操作（仅小号）

**最小验证标准**：在小号 alt 上，发送一条文字消息能成功送达；频率/夜间/黑名单硬闸任一越限即拒绝；主号 main 上写命令物理拒绝。

| 领域 | 标准 | 是否通过 |
|---|---|---|
| 战略对齐 | 写操作是否严格收敛在"小号+手动确认"边界内？ | ✅ |
| 进度绩效 | `wx-send.py` + `wechat-ui/` 是否在 alt 上实测通过？ | ✅ |
| 风险状态 | 是否从未在 main 上触发写操作？ | ✅（账号隔离纪律） |
| 风险状态 | 频率限制（1min≤3 / 1h≤20 / 同对象 5min≤2 / 23:00–08:00）是否代码级硬闸？ | ✅ |
| 交付物合规 | 发送前 OCR 校验聊天对象是否启用？ | ✅ |

**决策**：**Conditional Go**

| 条件 | 可测量标准 | owner | 截止日 |
|---|---|---|---|
| 小号连续 30 天零风控告警 | 无强制下线、无违规提示、无消息被吞 | 本人 | 2026-10-15 |
| 写操作冒烟纳入体系 | 发送/自动回复各 1 条用例进 `scripts/` 冒烟脚本（dry-run 模式） | 本人 | 2026-10-01 |

### G2 总决策

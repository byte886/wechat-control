# 05 · 治理卡 · wechat-control

> 补立项日期：2026-09-16 ｜ 方法：project-manager 的 monitor 模式——决策权 / 升级路径 / 决策节奏三件事。
> 个人场景两层压缩：本人 = PM + Sponsor；升级 = 暂停重评。

## 基本信息

- 目标：把微信本地数据安全只读地交给 AI 做查询与总结，小号受控发消息（见 `00_项目总纲.md`）。
- 截止：G3 治理整顿 2026-10-15；之后进入维护期，无硬截止。
- Owner：本人（单一开发者）。

## 我可以独立决定的范围

- **影响范围**：不改变项目目标与成功标准（总纲 §2 六条）的调整，可自决——包括文档结构、脚本内部重构、references 增补、MCP server 工具集微调、频率阈值在风控下限内的进一步收紧。
- **预算/支出**：本项目零现金支出，无预算概念；任何新增订阅/付费服务需自评估并记入 ADR。
- **时间**：不影响 G3 截止日（2026-10-15）的进度微调自决；若需推迟，记入 ADR。
- **技术路线**：在"只读为主 + 小号受控写"框架内的实现选择（如换 ASR、换推送渠道）可自决；触碰框架本身（如主号写、多开、Frida）不行。

## 必须暂停重评的触发条件（命中任一即停）

- [ ] **微信被迫升级到 4.1.10+**，`wx init` 失效 → 项目改 On Hold，等上游 wx-cli 跟进。
- [ ] **公开仓发现个人标识泄漏**（当前树或历史）→ 立即停止推送，走 T-03 流程，必要时 filter-repo。
- [ ] **写操作在主号 main 误触发** → 立即禁用写操作，复盘账号隔离为何失效。
- [ ] **小号收到微信风控告警**（强制下线 / 违规提示 / 消息被吞）→ 停写，30 天观察期。
- [ ] **双机同步出现非 ff 冲突** → 停止同步，核对"先子后父"纪律。
- [ ] **G3 成功标准连续两轮每周自查未达标** → 项目改 On Hold，季度评审重评。
- [ ] **SIP 被重新打开** → 重启后 `csrutil status` 自查，恢复 SIP 关闭前不跑 `wx init`。

## 碰节奏（governance cadence）

- **每周日晚 15 分钟三问自查**：
  1. 范围还对吗？（做的事是否还往总纲目标走）
  2. 进度还走得动吗？（距 G3 截止日还有几周，工单状态对不对）
  3. 风险有新的吗？（风险登记册是否要更新概率/影响）
- **每季度随 portfolio 批量评审**：过一次 G3，决定 Go / Conditional Go / Hold。
- **门节点**：G1（已追认 Go）→ G2（已 Conditional Go）→ G3（进行中，见 `02_阶段门评审.md`）。

## 升级路径（个人版 = 暂停重评流程）

1. 命中触发条件 → 项目状态改 On Hold。
2. 在 `00_项目总纲.md` §4 写一句"为什么暂停"。
3. 下次每周自查或季度评审时给 Go / Conditional Go / Hold / Kill 决策。
4. 恢复时先跑 `scripts/smoke.sh` 确认健康，再继续工单。

## 决策记录（ADR）

> 关键决策只写"为什么这么选、放弃了什么备选、什么时候该重新评估"，不记实现细节。

### ADR-001 · 为什么选 jackwener/wx-cli 做底座

- 日期：2026-09-14（回溯补记）
- 状态：Accepted

**背景**：要解密微信本地 SQLCipher 4 数据库，需要密钥提取 + SQL 解密两层能力。从零写要逆向微信内存布局，成本极高。

**决策**：底座选 `jackwener/wx-cli`（Rust 实现），只在其上做 Python/Shell 业务层。

**备选（被放弃）**：
- 方案 A：自己用 Python + lldb 扫微信内存提取密钥——放弃因为曾触发风控（见 ADR-003），且重复造轮子。
- 方案 B：用其他开源 wx 工具（如 hook 类方案）——放弃因为多依赖持续注入，红线。

**后果 / 何时重评**：wx-cli 上游若停更或 break，多账号能力已 fork 到 `third-party/wx-cli` 可自维护；单账号只读仍可回退 npm 官方版。重评触发：上游连续 6 个月无更新且出现不兼容。

### ADR-002 · 为什么不做微信多开

- 日期：2026-09-14（回溯补记）
- 状态：Accepted

**背景**：主号 + 小号同时在用，直觉方案是多开微信。

**决策**：不做多开；用"单官方 App 内切换账号 + `wx-account.sh`"方案。

**备选（被放弃）**：
- 方案 A：第三方多开工具——放弃因为技术不可行（微信对多开检测严格）且高风控。
- 方案 B：一台机登主号、另一台机登小号——放弃因为数据分散、AI 查询要跨机聚合，违背"本地只读"简洁性。

**后果 / 何时重评**：切换账号需要重新 `wx init`（密钥与账号绑定），有操作成本。重评触发：未来出现可靠且低风控的多开方案，或本人主/小号角色合并。

### ADR-003 · 为什么只读为主体，写操作严格隔离到小号

- 日期：2026-09-14（回溯补记）
- 状态：Accepted

**背景**：历史上做过 Frida hook + 重签微信的尝试，触发强制下线 + 违规提示，主号险些被封。

**决策**：只读为主体（碰本地文件、零风控）；写操作仅在小号 alt，且频率/夜间/黑名单/OCR 四级硬闸；主号 main 永远只读。

**备选（被放弃）**：
- 方案 A：主号也开放写操作图方便——放弃因为主号风控代价不可接受（社交资产在主号）。
- 方案 B：用微信协议层发消息（不走 UI）——放弃因为协议层更容易被风控识别为机器人。

**后果 / 何时重评**：写操作能力受限于 UI 自动化的稳定性（macOS 升级可能改 UI 元素）。重评触发：小号连续 30 天零风控后，可评估是否放宽频率（只收紧不放宽，谨慎）；主号写操作永远不开放。

### ADR-004 · 为什么仓设为 public 且坚持零隐私三归宿

- 日期：2026-09-14（回溯补记）
- 状态：Accepted

**背景**：个人工具要不要公开？公开则一切入仓内容全世界可见。

**决策**：仓设 public；个人数据严格三归宿——① 能脱敏成通用内容的脱敏后明文随仓；② 确需保留且无法脱敏的加密 `.enc` 随仓；③ 无保留价值的删除。不挪到仓库外。

**备选（被放弃）**：
- 方案 A：仓设 private——放弃因为失去公开仓的可备份/可展示价值，且 private 不等于安全（账号泄漏即泄漏全部）。
- 方案 B：个人数据放仓库外另一个私有目录——放弃因为双机同步时会散佚，且违背"数据归宿清晰"原则。

**后果 / 何时重评**：每次 push 前必须过隐私扫描（T-03）。重评触发：若公开仓被微信官方以"违反使用条款"施压，改 private 并走退役流程。

### ADR-005 · 为什么锁微信版本 4.1.8

- 日期：2026-09-14（回溯补记）
- 状态：Accepted

**背景**：微信 4.1.10+ 改变了密钥在内存中的存储格式，wx-cli 扫不到密钥，`wx init` 失败。

**决策**：锁版本 ~4.1.8，关闭微信自动更新，不主动升级。

**备选（被放弃）**：
- 方案 A：跟随微信升级、等 wx-cli 适配——放弃因为升级后立即不可用，适配周期不可控。
- 方案 B：自己 patch wx-cli 适配 4.1.10+——放弃因为 Rust 逆向成本高，且每次微信小版本升级都要跟。

**后果 / 何时重评**：一旦微信被迫升级（系统更新带升、官方强制），项目立即 On Hold。重评触发：上游 wx-cli 官方支持 4.1.10+ 并实测通过，可评估升级。

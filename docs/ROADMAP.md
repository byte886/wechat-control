## 第一阶段（补充）：写操作（发消息 / 自动回复）— 安全优先

> 用户明确要求：写操作也是需要的，但要尽量提供安全的方法。
> 核心原则：**只读为主，写操作为辅；人工审核，低频操作；先小号验证，再考虑大号。**

### 安全设计原则

| 原则 | 说明 |
|------|------|
| **1. 人工审核后发送** | AI 只起草消息，用户确认内容和接收人后才发送，绝不自动发送 |
| **2. 自动回复默认关闭** | 不做"收到消息自动回复"这种高频写操作；仅在小号探索性开启框架（见 W-4），默认关闭、不用于主号 |
| **3. 低频操作** | 限制发送频率，不做批量发送、不做营销群发 |
| **4. UI 自动化，不注入不修改** | 用 mac-system-toolkit 的界面自动化操作微信官方界面发消息，不注入微信进程、不修改微信二进制、不重签 |
| **5. 操作前二次确认** | 每次发消息前展示：接收人 + 消息内容，用户明确说"发送"后才执行 |
| **6. 先小号验证** | 写操作先在微信小号上测试，确认安全、不触发风控后，再考虑是否用于大号 |
| **7. 可随时撤回** | 发送后告知用户可在微信内撤回（2 分钟内），降低误发风险 |
| **8. 风控监控** | 发送后观察微信状态，如出现异常（强制下线/违规提示）立即停止所有写操作 |

### 写操作功能清单

| # | 功能 | 说明 | 安全等级 | 状态 |
|---|------|------|---------|------|
| W-1 | **发送文字消息** | 用户说"给XX发消息：内容"，AI 起草，用户确认后用 UI 自动化发送 | ⚠️ 中风险（操作微信界面） | ✅ 已完成（2026-09，send_message.sh 7步流程验证，默认模式 9.3s 实测） |
| W-2 | **发送图片/文件** | 给指定联系人/群发送本地图片或文件 | ⚠️ 中风险 | ⏳ 待开发 |
| W-3 | **@某人发消息** | 在群里 @指定成员发消息 | ⚠️ 中风险 | ⏳ 待开发 |
| W-4 | **自动回复（谨慎）** | 收到指定关键词时自动回复——**默认不做**，如用户明确要求，需人工审核每条回复内容，且限制频率和范围 | 🔴 高风险 | 🔄 探索中（框架已实现，仅小号测试，见 SKILL §6） |
| W-5 | **群公告/群管理** | 修改群公告、拉人/踢人等群管理操作 | 🔴 高风险 | ⏳ 暂缓 |
| W-6 | **防撤回 / 撤回恢复 / 代撤回** | 阻止对方撤回、恢复已撤回正文、工具代撤回 | 🔴 高风险 | ❌ 不做：稳定防撤回需注入/hook 微信进程，曾触发风控；监控落盘若在撤回前已抓取仅为 best-effort 偶然留痕，不承诺；工具发出的消息仅提示用户 2 分钟内手动撤回 |

### 写操作技术实现思路

- **工具**：mac-system-toolkit（cu plane，AppleScript + 坐标点击，见其 references）
- **流程**：激活微信 → 搜索联系人/群 → 打开聊天窗口 → 输入消息 → 用户确认 → 点击发送
- **不做**：不注入微信进程、不调用微信私有 API、不修改微信数据库、不重签微信
- **风控**：操作间隔 > 3 秒，不模拟人类无法达到的操作速度

## 附录 A：media_0.db 密钥提取方案研究（2026-09-10）

> 背景：微信 4.x 新语音存在加密的 media_0.db 中（BLOB 形式），而非单独 .silk 文件。
> 核心问题：如何在**不需要用户播放语音**的情况下提取 media_0.db 密钥？

> **✅ 2026-09-16 更新（结论已变，以此为准）**：实测**保持微信运行即可用 `wx init --force` 提取 media_0.db 密钥，无需播放任何语音**；语音收到后微信自动下载入库（`VoiceInfo.voice_data`，SILK BLOB），转写全程免播放。当日验证 `media_0.db` 可直接解密、`VoiceInfo` 有 1491 条语音。下方方案 A 的"播放一次触发"在当前 wx-cli/微信 4.1.8 上已非必要，仅作历史研究保留；方案 B（lldb hook）亦不再需要。新账号尚无语音消息时可跳过本步。

### 方案对比

| 方案 | 原理 | 风控风险 | 可行性 | 状态 |
|------|------|----------|--------|------|
| **A. 播放语音触发懒加载** | 微信懒加载数据库，播放语音触发 media_0.db 打开，密钥派生到内存，wx-cli 扫描提取 | 极低 | ✅ 已验证 | **当前使用** |
| **B. LLDB hook 捕获 raw_key** | 微信启动时 hook CCKeyDerivationPBKDF / PKCS5_PBKDF2_HMAC，捕获根密钥 raw_key，可派生所有数据库密钥 | 中（长时间附加可能被检测） | ⚠️ 研究中 | 已验证附加和断点设置，未捕获到调用（附加时机问题） |
| **C. 找 passphrase 存储位置** | 研究微信是否把 passphrase 存在 Keychain/配置文件中 | 低 | ❌ 不可行 | 已确认：密钥不在 Keychain，不以明文存磁盘，只在进程内存中 |
| **D. 复制已做好的数据库** | 把已提取密钥的 media_0.db 复制到目标环境 | 低 | ✅ 可行 | 仅限开发测试 |

### 方案 B（LLDB hook）实验结论

**已验证成功的部分：**
- ✅ lldb 成功附加到微信进程（Intel x86_64）
- ✅ 成功设置两个断点：CCKeyDerivationPBKDF + PKCS5_PBKDF2_HMAC
- ✅ 自动点击登录按钮成功（cliclick 坐标点击）
- ✅ 微信正常登录，无异常

**未成功的部分：**
- ❌ 未捕获到 PBKDF2 调用（20秒内计数为0）

**原因分析：**
1. **附加时机不对**：用户已手动打开微信，密钥已缓存，附加时不再触发派生
2. **正确方式**：应在微信启动前就用 `lldb -w -n WeChat` 等待模式附加
3. **等待模式问题**：之前测试等待模式时 lldb 没有成功附加（可能是进程名匹配问题）

**pandorafuture/wx-cli 参考实现：**
- GitHub：https://github.com/pandorafuture/wx-cli
- 核心：crates/wx-keychain/src/lldb.rs + script.rs
- 原理：Hook CCKeyDerivationPBKDF，捕获 raw_key（32字节 passphrase）
- enc_key = PBKDF2(raw_key, db文件头salt, 256000)
- **仅支持 arm64**，Intel 需适配寄存器（x1-x6 → rsi/rdx/rcx/r8/r9 + 栈）

**Intel 适配脚本：** 实验性脚本，同时 hook 两个函数（临时产物，未纳入仓库留存）

### 微信 4.x 加密机制关键发现

1. **不是标准 SQLCipher**：微信 4.x 直接用内存中的值当 AES-256 key，不做标准 PBKDF2 派生（掘金文章实测）
2. **密钥格式**：`x'<64hex_enc_key>'`，存在内存中作为 NSData 对象，通过 DBEncryptInfo 单例访问
3. **懒加载**：数据库只有在被打开时才派生密钥到内存，media_0.db 需播放语音才打开
4. **跨平台不可复用**：Mac 与 Windows 的 key 不能直接复用，需各平台重新提取
5. **图片密钥例外**：图片密钥可从磁盘 kvcomm 缓存派生，不需要进程内存

### 当前推荐

- **生产环境（2026-09-16 起）**：微信运行中直接 `wx init --force` 即可提取 media_0.db 密钥，**无需播放语音**；密钥同账号同版本一次提取长期有效
- ~~方案 A（播放一次触发）~~：当前版本已非必要，保留作历史
- ~~方案 B（LLDB hook）~~：免播放已实现，不再投入
- **开发测试**：方案 D（复制已做好的数据库）

# 微信助手（wechat-control）产品需求文档（PRD）

> 版本：v1.0
> 日期：2026-09-10
> 状态：第一阶段已完成，第二/三阶段进行中

---

## 一、产品概述

### 1.1 背景

微信已成为中国人最主要的通讯工具，但随着群聊和联系人增多，用户面临普遍痛点：
- **信息过载**：工作群、家庭群、兴趣群消息999+，重要信息被淹没
- **语音不便**：语音消息在开会、通勤等场景无法收听，逐条转文字效率低
- **历史难查**：微信自带搜索能力有限，找半年前的消息如同大海捞针
- **监控缺失**：重要群的消息无法及时获知，错过 @自己 的通知
- **总结困难**：几百条消息需要人工梳理，耗时耗力

现有解决方案（如 itchat、wechaty、OpenClaw）普遍存在**封号风险高**、**功能有限**、**隐私不安全**等问题。

### 1.2 产品定位

**一个安全、只读、本地运行的微信信息管理助手。**

核心价值：
- **安全**：不注入、不重签；写操作仅限小号探索性开启（发消息/自动回复），主号只读，封号风险极低
- **高效**：查询、总结、监控、语音转文字一站式解决
- **私密**：所有数据本地处理，不上传云端

### 1.3 目标用户

| 用户类型 | 核心需求 |
|---------|---------|
| 上班族 | 工作群消息管理、重要消息不遗漏、聊天记录快速查找 |
| 群主/管理员 | 大群监控、消息总结、群成员管理 |
| 销售/商务 | 客户消息管理、语音转文字、历史记录检索 |
| 家长 | 家长群通知监控、重要消息提醒 |
| 项目负责人 | 多项目群并行管理、进展对比、话题梳理 |

### 1.4 产品目标

- **短期（v1.0）**：实现只读查询 + 语音转文字 + 基础监控，满足核心信息获取需求
- **中期（v2.0）**：完善监控推送 + AI 总结 + 飞书同步，形成完整的信息管理闭环
- **长期（v3.0）**：安全的写操作（发消息）+ 多平台支持（Windows）+ 多账号管理

## 二、功能需求

### 2.1 模块一：只读查询（P0，已完成）

**需求描述**：用户可以查看所有私聊和群聊的列表，包含会话名称、未读数、最后一条消息、最后消息时间。

**用户故事**：

#### 2.3.6 MCP 连接器（已完成，2026-09）

把监控/查询能力以 STDIO MCP 服务暴露给豆包桌面端，在连接器市场以"自定义连接器"安装。

- 服务：`mcp-server/server.py`（fastmcp，服务名 `wechat-monitor`），提供 5 个工具：`get_new_messages`、`get_monitor_status`、`mark_messages_as_read`、`update_config`、`get_message_history`。
- 配置（豆包桌面端「连接器·技能·伙伴」→「连接器」tab → 自定义，STDIO）：命令填 `mcp-server/.venv/bin/python` 的绝对路径，参数填 `server.py` 的绝对路径。
- 已修复：豆包 GUI（launchd）拉起连接器时 `PATH` 仅 `/usr/bin:/bin:/usr/sbin:/sbin`，`shutil.which("wx")` 会返回 None；现 `_resolve_wx_bin()` 按 which → `/usr/local/bin/wx`（Intel）→ `/opt/homebrew/bin/wx`（Apple Silicon）→ `wx` 回退。
- 重启方式：豆包连接器开关关→开（直接 kill 进程对 STDIO 托管进程无效）。
- 边界：MCP 工具为只读查询/状态管理；MCP 服务**主动 notification 冒泡**经验证客户端不唤起，故实时外推仍走 §2.3.3 的邮箱通道。

#### 2.3.7 合并聊天记录识别与拆分（监控子功能，待办）

**需求描述**：别人转发来的"合并聊天记录 / 收藏卡片"在工具里只是一条卡片、CLI 只显示前 10 条。需要**自动识别这类消息**，并把其中**每条子消息拆分还原**为结构化内容；实时监控收到时自动展开、纳入重要性判定与总结/提醒，历史查询也能对任意一/多条手动展开。

**用户故事**：
> 作为用户，有人甩给我一份上百条的合并聊天记录，我不用逐条点开，工具能直接把里面谁说了什么、什么时间、有哪些链接/图片拆出来并总结；监控群里出现合并记录时也不会被当成一条卡片漏掉。

**验收标准**：
- [ ] 识别合并记录类型消息（`local_type=81604378673`，appmsg recorditem），**不限会话、不限最新一条**
- [ ] 拆分每条子消息：发送人、时间、消息类型、文本内容、链接 URL
- [ ] 图片/语音/视频等子媒体可定位，并复用既有附件导出 / 语音转写链路处理
- [ ] 实时监控收到合并记录时自动展开，子消息纳入重要性判定与每日总结
- [ ] 历史查询可对指定的一/多条合并记录手动展开
- [ ] 通用：不局限于特定来源（如豆包链接），任意合并记录都能拆

> 现状（2026-09）：直读 `message_0.db` + zstd 解压 + 解析 recorditem 的路径已验证（文件传输助手两份记录合并去重 124 条链接，方法见 [advanced-usage.md](../references/advanced-usage.md) §5）；**通用拆分脚本未固化**。注意 CDATA 内 `<desc>` 只是前 5 条 + 字面 `...` 的截断摘要，完整子消息必须解析整条解压 XML，不能只取 desc。

### 2.6 模块六：写操作（P2，开发中）

> 核心原则：只读为主，写操作为辅；人工审核，低频操作；先小号验证。
>
> **重要说明**：本模块中的"自动回复"功能为**探索性质**，本质上是客服（企业微信）场景更需要的能力，普通用户即使有需求也是轻需求。本阶段目标是**验证能做到什么程度**，不作为核心功能推广。自动回复仅在微信小号上测试，绝不在大号使用。

#### 2.6.1 发送文字消息（手动确认模式）

**需求描述**：用户说"给XX发消息：内容"，AI 起草，用户明确说"发送"后执行。

**用户故事**：
> 作为用户，我想对指定联系人/群发文字消息，不用切换到微信手动操作，但发送前必须确认，以免发错。

**验收标准**：
- [x] AI 解析接收人和内容，展示"接收人：XX，内容：XXX"
- [x] 用户必须明确说"发送"才执行；说"好""对""嗯"不发送
- [x] 接收人不存在时，AI 列出候选反问，不猜测不发送（发送前另有 OCR 聊天标题验证兜底）
- [x] 用户说"改一下：新内容"时，更新内容重新展示
- [x] 用户说"算了/取消"时，中止不发送
- [x] 用 UI 自动化操作微信官方界面（Cmd+F 键盘操作 + cliclick/OCR，见 SKILL §6 与本文附录 C）
- [x] 不注入微信进程、不调用私有 API、不重签微信
- [x] 操作间隔 >3 秒，不模拟人类无法达到的速度
- [x] 发送后立即提示"已发送，可在2分钟内撤回"

#### 2.6.2 发送图片/文件（后续阶段）

**验收标准**：
- [ ] 支持发送本地图片

## 附录 A：第一阶段实现决策与测试（原 wechat-ai-agent-spec.md）

### A.1 实现决策（已定，含取舍）

- **只读不写**：第一阶段只做数据读取和 AI 总结，不做发消息、自动回复、加好友等写操作。放弃 UI 自动化发消息方案，因为操作微信界面有风控风险。
- **先按需查询，再主动监控**：第一优先级是用户主动提问触发查询；定时自动监控推送作为第二阶段。放弃一开始就做定时任务，因为先验证基础链路稳定性更重要。
- **第一阶段只在豆包对话回答**：不同步飞书文档/知识库。放弃一开始就做飞书同步，因为先验证核心价值，输出通道是次要的。
- **自然语言交互**：用户用自然语言提问，豆包解析意图后调用 wx-cli。放弃固定命令模板，因为自然语言在豆包对话中最自然。
- **默认简短要点 + 重要消息标注**：总结默认 3-5 条核心结论，重要消息自动加粗标注；用户说"详细点"时切换到详细分类。
- **密钥提取方式：关 SIP + sudo + 不重签微信**：已验证成功（16/18 个密钥）。放弃 ad-hoc 重签微信方案，因为重签会改变 code identity，可能触发微信风控（之前重签后被强制下线+违规提示）。
- **微信版本锁定 4.1.8**：wx-cli 当前只支持 ~4.1.8，微信 4.1.10+ 改变了密钥存储格式导致提取失败。这是 wx-cli 的硬性限制。
- **密钥长期有效**：同账号、同版本、不重装的情况下，密钥提取一次后永久有效。仅在微信升级、切换账号、重装时重新提取。
- **用微信小号不用主号**：所有操作针对小号数据目录，不碰主号数据。

### A.2 测试决策

- **测试接缝**：wx-cli 命令行接口。所有查询都通过它，接口稳定；上层意图解析和 AI 总结可反复改写，只要命令调用正确、输出解析正确，链路就不会坏。
- **覆盖边界**：正常场景（群名/时间/关键词明确）、边界场景（歧义、超长时间、无匹配、空群）、异常场景（密钥失效/数据库损坏/微信未运行）、风控验证（读取不弹警告、不被强制下线）。
- **测试顺序**：先验证 wx-cli 基础命令 → 再验证自然语言意图解析 → 最后验证 AI 总结质量，全程监控微信状态。

### A.3 第一阶段 User Stories（8 条，已全部验收）

| **UI 自动化（选定）** | 不注入不重签，风控低；操作可见可撤回 | 依赖界面布局，版本更新可能失效 | 风控安全第一 |
| 协议模拟（itchat/wechaty） | 功能强大，可后台 | 封号风险极高 | 不可接受 |
| 注入/Hook（Frida） | 可调内部 API | 需重签，触发风控 | 曾触发强制下线+违规提示 |
| AppleScript 直接发 | 简单 | 微信 AppleScript 支持有限 | 功能不足 |

### C.2 发送执行流程（UI 自动化 10 步）

1. 激活微信（AppleScript）
2. Cmd+F 打开搜索
3. 输入接收人名称
4. 等待搜索结果（sleep 1-2 秒）
5. 回车选择第一个结果
6. 等待聊天窗口打开（sleep 1-2 秒）
7. 输入消息内容
8. 回车发送
9. 等待发送完成（sleep 1 秒）
10. 提示"已发送，可在 2 分钟内撤回"

### C.3 自动回复流程

1. 后台轮询新消息（复用 wx-cli new-messages，每 5 分钟）
2. 检查触发条件：关键词匹配？特定人/群？夜间（23:00-08:00 只记录）？频率上限？
3. 触发后 AI 生成回复内容
4. 安全过滤：10 类黑名单检查 → 命中则不发送、记录日志、通知用户
5. 执行发送流程（同手动 UI 自动化）
6. 记录日志 + 通知用户

### C.4 安全过滤黑名单（10 类）

1. 💰 金钱相关：转账、付款、红包、价格、金额、支付宝、微信支付、银行卡
2. 🔑 隐私敏感：密码、验证码、身份证、手机号、地址、个人信息
3. 📝 承诺保证："我保证""一定""肯定""没问题""包在我身上"
4. 🚫 敏感内容：政治、色情、暴力、赌博、毒品
5. 😠 辱骂攻击：脏话、骂人、歧视、威胁
6. 🏢 公司机密：内部数据、未公开信息、商业秘密
7. ⚕️ 专业建议：医疗诊断、法律意见、投资建议
8. 🎭 身份冒充："我是本人""是我""你连我声音都听不出来了"
9. 🤖 暴露 AI："我是 AI""自动回复""机器人"
10. ❓ 反问质疑："你是谁""你怎么知道"

### C.5 频率限制

| 维度 | 限制 |
|------|------|
| 全局每分钟 | ≤3 条 |
| 全局每小时 | ≤20 条 |
| 同一个人/群 | 5 分钟内 ≤2 条 |
| 夜间 | 23:00-08:00 自动暂停 |

手动发消息 US-1~US-5、自动回复 US-6~US-14。验收标准见正文 §2.6。

### C.8 测试用例

**手动发消息（T-1~T-6）**：小号自发测试、不存在联系人反问、非"发送"词不发送、修改内容、取消中止、撤回提示。

**自动回复（T-7~T-15）**：关键词触发、特定人触发、未配置不回复、黑名单拦截、频率超限拒绝、夜间静默、暂停/恢复、通知内容完整。

**风控验证**：测试期间观察微信状态（强制下线/违规提示/功能限制），测试后检查账号正常。

### C.9 风险与应对

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| 微信版本更新致 UI 布局变化 | 中 | 中 | 锁版本、关自动更新；失效后更新流程 |
| 自动回复触发风控 | 高 | 低 | 严格频率+黑名单；仅小号；异常即停 |
| 搜索结果不准发错对象 | 高 | 中 | 发送前展示确认 + OCR 聊天标题验证 |
| cliclick 输入中文失败 | 中 | 中 | 备用 AppleScript keystroke 或剪贴板粘贴 |
| 微信窗口被遮挡 | 中 | 中 | 操作前激活前置；失败重试最多 3 次 |
| 自动回复内容不合适 | 中 | 中 | 10 类黑名单；随时暂停；日志可查 |

### C.10 不做什么

**本阶段不做**：发送图片/文件/@消息、自动回复图形配置界面、多账号自动回复切换、朋友圈/公众号自动回复、群管理操作、定时发送、批量/营销群发、消息撤回操作、已发送消息编辑/删除。

**永远不做（安全底线）**：不注入进程、不重签微信、不调用私有 API、不修改数据库、不在大号测试自动回复、不做绕过风控的操作。

### D.1 核心需求（一句话）

让 AI 能用自然语言查询和总结微信本地数据（只读为主），并在严格风控下仅对小号开放受控发消息；工具本身可公开、可双机同步、可冒烟验证。

### D.2 用户场景

### D.5 治理整顿 User Stories（US-1~US-10）

> 角色：使用本技能的 AI Agent / 本人。治理整顿期（G3 发布门）的可验收行为，不改三阶段能力本身。

- **US-1 只读查询一致性**：任一只读命令后，微信数据库 mtime 不变、无出站连接、无微信 UI 弹窗。
- **US-2 版本锁定可验证**：一条命令确认微信版本=4.1.8 且自动更新关闭，30 秒内判断。
- **US-3 写操作账号隔离**：主号 main 上触发发送命令时物理拒绝，打印"写操作仅限小号 alt"。
- **US-4 写操作频率硬闸**：连发 4 条（同对象）第 3 条后被拒；夜间任一条被拒；拒绝事件落日志。
- **US-5 发送前对象校验**：OCR 当前微信窗口标题，确认接收方匹配后才发送；不匹配时停止并二次确认。
- **US-6 隐私零泄漏**：扫描命令在公开仓当前树查无真实 wxid/手机号/昵称/Msg_<MD5> 分表清单。
- **US-7 双机一致**：两台机 checkout 同一 commit 后，冒烟命令退出码相同。
- **US-8 可移植性**：全仓无硬编码用户名路径，用 ~ 或相对路径。
- **US-9 冒烟一键化**：scripts/smoke.sh 一条命令跑完 10 类只读 + 写操作 dry-run，退出码 0 即健康。
- **US-10 MCP server 可用**：STDIO 连接后至少能调用 3 个只读工具（sessions/search/unread）。

### D.6 治理实现决策

- 底座：Rust wx-cli 做密钥提取与解密，Python 做上层业务，Shell 做账号切换与 UI 自动化
- 语音：SILK V3 解码走 tools/silk-v3-decoder，ASR 走本地 FunASR SenseVoiceSmall，不上云
- 存储：公开仓 + 三归宿；含个人数据的文件不入库
- 测试接缝：所有治理行为收敛到 scripts/smoke.sh，冒烟通过=健康
- 不测：FunASR 模型精度、微信 UI 像素位置、真实发送成功（走 dry-run）

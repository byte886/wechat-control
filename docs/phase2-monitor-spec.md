# 微信群 AI Agent · 第二阶段规范（主动监控推送 + 飞书同步）

> 基于第一阶段（只读查询+AI总结）的成果，扩展主动监控、实时推送、飞书同步能力。

## 1. 问题是什么

第一阶段实现了**按需查询**（用户问什么查什么），但缺少：
- **主动监控**：用户不能 24 小时盯着微信，重要消息（@我、紧急通知）可能错过
- **实时推送**：有重要消息时需要立即通知用户，而不是等用户主动问
- **定期总结**：每天/每周的群聊总结需要自动生成，不用用户手动查
- **飞书存档**：重要的总结需要同步到飞书知识库，方便长期检索和跨设备查看

## 2. 方案是什么

### 2.1 整体架构

```
微信本地数据库
    ↓ (wx new-messages 增量查询，5-10分钟轮询)
监控引擎 (monitor.py)
    ├─ 重要消息判定 (@我/关键词/特定人)
    │   └─ 实时推送 → 豆包通知
    └─ 常规消息积累
        └─ 每日 21:00 触发总结
            ├─ AI 总结 (话题聚类+重要消息)
            ├─ 豆包推送
            └─ 飞书文档同步 (AI知识库→微信自动化→监控总结)
```

### 2.2 核心组件

1. **监控配置文件** (`~/.wx-cli/monitor_config.json`)：存储监控群列表、关键词、特定人、推送规则
2. **监控引擎**：轮询 new-messages，判定重要消息，触发推送
3. **每日总结**：每天 21:00 生成各监控群的当日总结
4. **飞书同步**：把总结写入飞书文档
5. **推荐话术**：AI 分析 sessions+stats，给出监控群推荐列表，用户选择

> 实现落点：上述 2/3/4 并未拆成独立文件，而是合并为单个 `scripts/wx-monitor.py` 的子命令（monitor / daily / daily --sync / recommend / config）；准实时监听另有 `scripts/realtime-monitor.py`。

## 3. User Stories（可验收）

### US-1：初始监控群推荐
> 作为用户，当我第一次启动监控时，系统应分析所有群的活跃度和人数，给出推荐列表，我选择后加入监控。
- 验收：运行 `wx-monitor recommend`，输出按活跃度排序的群列表（群名、消息量、人数、推荐理由），用户输入序号后写入配置

### US-2：重要消息实时推送
> 作为用户，当监控群里有人 @我 或发了关键词消息时，我应在 5-10 分钟内收到豆包通知。
- 验收：在测试群发 @小号昵称 的消息，5-10 分钟内豆包收到通知（包含发送人、时间、消息内容、群名）

### US-3：自定义关键词
> 作为用户，我可以添加自定义关键词（如"紧急"、"截止"），包含这些词的消息也会实时推送。
- 验收：配置关键词"测试"，在群里发包含"测试"的消息，收到实时推送

### US-4：指定特定人
> 作为用户，我可以指定特定人（如老板、家人），他们发的任何消息都会实时推送。
- 验收：配置某联系人为特定人，该联系人发任何消息都收到实时推送

### US-5：不重要消息忽略
> 作为用户，普通聊天、图片、视频等不重要消息不会实时推送，只在每日总结里出现。
- 验收：在群里发普通文本（不含@我/关键词），不收到实时推送；每日总结里包含该消息

### US-6：每日总结
> 作为用户，每天晚上 9 点我应收到当日所有监控群的总结（话题聚类+重要消息+未读提醒）。
- 验收：运行 `wx-monitor daily`，输出各群的当日总结（核心话题、重要消息、消息量统计），推送到豆包

### US-7：飞书同步
> 作为用户，每日总结应同步到飞书知识库（AI→豆包→微信自动化→监控总结），按日期组织。
- 验收：运行 `wx-monitor daily --sync`，飞书知识库中创建/更新当日总结文档

### US-8：监控配置管理
> 作为用户，我可以添加/移除监控群、关键词、特定人，查看当前配置。
- 验收：`wx-monitor config add-group <群名>` / `remove-group` / `list` 正常工作

### US-9：性能保护
> 作为用户，当监控群过多或消息量过大时，系统应提醒我，并建议降低频率或减少监控群。
- 验收：监控超过 20 个群或单次 new-messages 返回超过 500 条时，输出性能提醒

### US-10：消息类型识别
> 作为用户，推送和总结中应正确识别所有消息类型（文本/图片/视频/语音/位置/名片/链接/系统），视频/语音提示需在微信查看。
- 验收：群里发各种类型消息，推送/总结中正确标注类型，视频/语音提示"需在微信查看"

## 4. 已定的实现决策

### 4.1 技术选型
- **轮询方式**：`wx new-messages` 增量查询（不是全量 history），性能影响小
- **轮询频率**：默认 5 分钟（可配置 1-30 分钟）
- **推送通道**：豆包内通知（通过 AI 对话推送）+ 飞书文档（通过 lark-cli）
- **配置存储**：`~/.wx-cli/monitor_config.json`（JSON 格式，人类可读）
- **状态存储**：`~/.wx-cli/monitor_state.json`（上次查询时间、已推送消息 ID 等）

### 4.2 重要消息判定规则（优先级从高到低）
1. @我 或 @all（必须推送）
2. 自定义关键词匹配（用户配置）
3. 特定人发送的消息（用户配置）
4. 系统消息（入群/退群/撤回，可选推送）
5. 其他 → 不实时推送，只进每日总结

### 4.3 飞书文档组织
- 位置：AI 知识库 → 豆包 → 微信自动化 → 监控总结（新建子节点）
- 按日期组织：每天一个文档（如"2026-09-10 微信群监控总结"）
- 文档内容：各监控群的当日总结（核心话题、重要消息、消息量统计、未读提醒）

### 4.4 推荐话术流程
1. AI 运行 `wx sessions` 获取所有会话
2. 对每个群运行 `wx stats` 获取消息量和活跃度
3. 按活跃度（近7天消息量）排序，取 Top 10
4. 输出推荐列表（群名、消息量、人数、推荐理由）
5. 用户输入序号选择，写入配置
6. 用户也可以手动添加不在推荐列表的群

### 4.5 放弃的备选及理由
- **实时 WebSocket 推送**：微信没有开放的推送 API，无法实现真正的实时；5-10 分钟轮询是合理的折中
- **微信内推送**：需要操作微信界面发消息，有风控风险；先记录到需求池，后续用安全方式实现
- **语音转文字**：~~当时判断语音文件拿不到~~ 已解决——SILK 语音 BLOB 直接存在 media_0.db 的 VoiceInfo 表，由 voice-transcribe.py（silk 解码 + FunASR 本地转写）实现，见 references/voice-pipeline.md，无需第三方 API
- **小程序链接解析**：微信 4.1.8 不支持小程序链接展示，是版本限制，无法绕过

## 5. 测试决策

### 5.1 测试环境
- 测试群：〈测试群 chatroom ID〉（3人，消息类型丰富；真实 ID 不写入公开档）
- 测试账号：小号（配置名 alt；真实 wxid 用 wx-account.sh list 现查，不写入公开档）
- 微信版本：4.1.8

### 5.2 测试用例
1. **推荐功能**：运行 recommend，验证输出格式和排序
2. **@我推送**：在测试群发 @小号昵称，验证 5-10 分钟内收到推送
3. **关键词推送**：配置关键词"测试"，发包含"测试"的消息，验证推送
4. **特定人推送**：配置某联系人为特定人，该联系人发消息，验证推送
5. **普通消息不推送**：发普通文本（不含@我/关键词），验证不推送
6. **每日总结**：运行 daily，验证总结内容完整（话题聚类+重要消息+统计）
7. **飞书同步**：运行 daily --sync，验证飞书文档创建/更新
8. **配置管理**：add-group / remove-group / list 验证
9. **消息类型识别**：发各种类型消息，验证推送/总结中正确标注
10. **性能保护**：模拟大量消息，验证性能提醒

## 6. 不做什么（Out of scope）

- ❌ 微信内推送（发消息到微信/微信群）：有风控风险，记录到需求池，后续用安全方式实现
- ❌ 公众号通知：需要公众号 API 权限，记录到需求池
- ❌→✅ 语音转文字：已由 voice-monitor.py / voice-transcribe.py 实现（直读 media_0.db + 本地 ASR），见 references/voice-pipeline.md
- ❌ 视频/语音文件导出：微信需点击下载才保存到本地，且 wx-cli 不支持
- ❌ 小程序链接解析：微信 4.1.8 版本限制
- ❌ 自动回复：写操作，高风险，第三阶段再考虑
- ❌ 发消息：写操作，高风险，第三阶段再考虑
